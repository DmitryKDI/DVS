# Design

## Context

Репозиторий содержит документацию DVS и локальную заглушку диагностики. Внешние материалы пока не подтверждены. Концепция 2.0 добавляет возможности поверх базового сценария. Официальный старт по уставу DVS — 26.11.2026 в 10:00 МСК.

## Goals / Non-Goals

**Goals:** Один путь для механика, одна проверяемая граница для каждого источника и возможность заменить тестовые данные реальными по мере подтверждения контрактов.

**Non-Goals:** Собственная модель ML, прогноз остаточного ресурса и автоматическое назначение ремонта.

## Decisions

1. Предлагаемый модульный монолит из архитектуры DVS. Интерфейс показывает автопарк, результат проверки, доказательство и черновик. Backend связывает реестр, диагностику, документы и заявки через внутренние границы. Подтвердить стек по стартовым материалам.
2. Локальный прогон переиспользует `dvs.diagnostics` при явном включении тестового режима. Реестру, документам и ТОиР в таком прогоне достаточно синтетических учебных данных и тестового приёмника. Реальные адаптеры реализуются по проверенным схемам, примерам и ответам стендов. Синтетический путь исключает отправку на внешний стенд.
3. Перед объяснением проверяется связь «автомобиль → двигатель → документ → страница». Сохраняются ссылка на исходный документ, индекс страницы и отдельно печатный номер при наличии. В P1 добавляются координаты фрагмента, если их можно проверить по документу.
4. Подтверждение привязано к версии заявки. Вызов ТОиР выполняется через отдельный адаптер только после проверки актуальности подтверждения. Фиксируются факт и исход попытки. Неопределённый исход требует сверки перед повторной отправкой.
5. P1 подключается после приёмки P0. История использует сопоставимые проверки, интерактивная дефектовка сохраняет ответы механика, а карточка раскрывает основания каждой операции. P2 оформляется отдельно. Планировщик передаёт срочные и неясные случаи специалисту. Обратная связь связывает фактический результат с машиной, заявкой и контрольной проверкой.

## Risks / Trade-offs

- Неизвестные поля и пороги могут потребовать изменения внутренних моделей после сверки OpenAPI.
- Без проверенных PDF можно проверить путь интерфейса на синтетическом примере. Доказательность реальной процедуры проверяется по оригиналу.
- История при несопоставимых условиях не позволяет интерпретировать разницу оценок ML как ухудшение.

## Сверка локального каркаса

DEC-002 определяет проверку версии заявки. DEC-003 требует связи процедуры с документом и страницей. DEC-004 оставляет внешние схемы до сверки с OpenAPI. В локальном прогоне страницу и точную цитату подтверждает синтетическое руководство в памяти. Доказательство содержит индекс страницы и отдельный печатный номер. Проверка реального PDF и его применимости остаётся частью стендовой задачи.

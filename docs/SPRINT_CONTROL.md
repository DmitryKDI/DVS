# Управление 48-часовым спринтом

## 1. Цель управления

Сохранять единый приоритет, предотвращать конфликтующие изменения и обеспечивать проверяемое состояние продукта на каждой контрольной точке.

## 2. Единый владелец очереди

Дмитрий управляет очередью задач общего Codex и принимает решения о приоритетах. Исполнители могут готовить требования и проверять результаты параллельно, но конкурирующие команды на изменение общего рабочего дерева не запускаются.

## 3. Классы задач

- P0 — блокирует основной сценарий, достоверность или безопасность.
- P1 — повышает надёжность и удобство, но не блокирует основной путь.
- P2 — улучшение, которое можно исключить без ущерба приёмке.

При конфликте времени P0 имеет абсолютный приоритет.

## 4. Контрольные точки

| Время от старта | Ожидаемый результат | Решение руководителя |
|---|---|---|
| +0.5 ч | Материалы и доступы приняты | Зафиксировать блокировки |
| +2 ч | Контракты и среда проверены | Разрешить интеграцию |
| +7 ч | Первый проверенный ML-результат | Продолжить вертикальный срез |
| +13 ч | PDF evidence с корректной страницей | Разрешить связку |
| +20 ч | Диагностика + evidence + объяснение | Разрешить заявку |
| +26 ч | Заявка с подтверждением и ответ ТОиР | Полная интеграция |
| +32 ч | Сквозной сценарий | Заморозить новые функции |
| +38 ч | Негативные тесты и регрессия | Только P0 исправления |
| +44 ч | Чистый запуск и демо готовы | Финальная проверка |
| +48 ч | Сдача | Подтвердить отправку |

Это целевые контрольные точки, а не обещание, что зависимые работы завершатся автоматически.

## 5. Правила эскалации

Немедленно эскалировать:
- изменение OpenAPI;
- несовпадение документации и фактической заглушки;
- неизвестный статус ML;
- невозможность подтвердить страницу PDF;
- неоднозначность применимости процедуры;
- риск отправки дублирующей заявки;
- утечку секрета;
- потерю или конфликт данных;
- P0 дефект.

## 6. Правило заморозки

После появления сквозного сценария новые P1/P2 функции не добавляются, если они увеличивают риск регрессии. Исправляются P0 дефекты, проводится регрессия, фиксируется состояние.

## 7. Ежечасный отчёт

Каждый исполнитель сообщает:
- завершённые задачи;
- тесты и фактические результаты;
- изменённые файлы и коммиты;
- блокировки;
- риск для P0;
- следующий шаг.

## 8. Критерий готовности к сдаче

- P0 E2E пройден;
- негативные сценарии безопасности пройдены;
- clean start воспроизводим;
- README точен;
- секреты отсутствуют;
- демо отражает реальную функциональность;
- все незакрытые ограничения раскрыты.

# Quick Start — первые часы спринта

Дата старта: 26.11.2026, 10:00 МСК.  
Дедлайн: 28.11.2026, 10:00 МСК.  
Назначение: сократить время от открытия конкурсных материалов до первого проверенного сквозного результата.

## 0. До старта

Разрешённая подготовка:
- изучить и систематизировать опубликованные условия;
- подготовить архитектурную и организационную документацию;
- распределить роли;
- подготовить список недостающих материалов;
- проверить доступ участников к GitHub;
- подготовить список вопросов организаторам;
- согласовать процесс Git и отчётности.

Не выполнять до разрешённого времени:
- конкурсную реализацию;
- создание конкурсных рабочих промптов;
- создание реализационных конфигураций;
- построение поисковых индексов;
- иные действия, прямо запрещённые правилами конкурса.

Если точная граница разрешённой подготовки вызывает сомнение, получить письменное подтверждение организатора.

## 1. 10:00–10:30 — входной контроль

Руководитель проекта:
1. фиксирует время старта;
2. сохраняет актуальную версию правил и комплект исходных файлов;
3. проверяет, что все члены команды имеют доступ;
4. назначает одного человека ответственным за приём исходных материалов;
5. создаёт запись в журнале изменений;
6. проверяет чистоту рабочей ветки и отсутствие случайных секретов.

Backend:
1. открывает OpenAPI ML и ТОиР;
2. сверяет спецификации с работающими заглушками;
3. сохраняет проверенные схемы и примеры в разрешённом месте;
4. составляет список расхождений.

Frontend/QA:
1. проверяет пользовательские сценарии и требования;
2. подготавливает список экранов и состояний;
3. заводит тестовый журнал;
4. фиксирует тестовые идентификаторы автомобилей и диагностик только из исходного набора.

Выход этапа: входной комплект проверен; критические блокировки названы.

## 2. 10:30–12:00 — контракты и запуск окружения

- Сверить поля запроса/ответа ML.
- Сверить формат заявки ТОиР.
- Проверить фактические коды ошибок.
- Проверить загрузку vehicles.json и диагностических данных.
- Зафиксировать реальные команды установки и запуска.
- Не начинать параллельную реализацию на неизвестных схемах.

Контрольная точка: минимальное окружение запускается воспроизводимо; интеграционные контракты подтверждены.

## 3. 12:00–17:00 — вертикальный срез диагностики

Цель — получить один реальный ответ ML для одного автомобиля по исходным данным.

- Реализовать минимальный ML Adapter.
- Обработать timeout, transport error, validation error и бизнес-статус раздельно.
- Сохранить исходный ответ и нормализованное представление.
- Отобразить состояние в минимальном UI или проверяемом API.
- Проверить нормальный и аномальный примеры, если они предоставлены.

Не добавлять интерпретацию полей, смысл которых не подтверждён.

## 4. 17:00–23:00 — PDF и доказательства

- Проверить структуру всех шести PDF.
- Извлечь текст с привязкой к физической странице PDF.
- Отдельно проверить страницы с таблицами, схемами и сканами.
- Реализовать фильтрацию по двигателю и типу документа.
- Вывести найденный фрагмент и источник.
- Сверить каждый критичный результат с оригинальным PDF.

Контрольная точка: один проверенный запрос возвращает фрагмент из подходящего документа с правильной страницей.

## 5. 23:00–27.11 06:00 — связка диагностики и документации

- Соединить нормализованную диагностику с поиском процедуры.
- Разделить факты диагностики, предположения и положения руководства.
- При отсутствии подтверждённой процедуры не генерировать ремонтную инструкцию.
- Провести негативные тесты на несовместимый двигатель и отсутствие evidence.

## 6. 06:00–12:00 — ТОиР и интерфейс

- Сформировать черновик заявки только из проверенных данных.
- Отобразить все поля перед подтверждением.
- Подтверждать именно версию/снимок содержимого.
- После изменения черновика сбрасывать подтверждение.
- Отправлять только по фактическому контракту.
- Отображать реальный ответ заглушки.

## 7. 12:00–18:00 — сквозная интеграция

Пройти сценарий:
автомобиль → диагностика → документ → evidence → объяснение → черновик заявки → подтверждение → ТОиР.

Параллельно проверить нормальную диагностику и сценарии отказа.

## 8. 18:00–23:00 — QA и регрессия

- прогнать unit и integration тесты;
- выполнить негативные сценарии;
- проверить все семейства двигателей;
- проверить дублирование отправок;
- проверить ошибки внешних API;
- устранить P0 дефекты;
- запретить новые функции, если они угрожают стабилизации.

## 9. 23:00–28.11 04:00 — стабилизация

- заморозить scope;
- исправлять только дефекты;
- повторять полный регрессионный набор;
- проверить чистый запуск;
- проверить README;
- зафиксировать известные ограничения.

## 10. 04:00–10:00 — сдача

- записать непрерывное демо до 3 минут;
- проверить, что демонстрируемый сценарий реально работает;
- проверить открытый репозиторий и инструкции;
- проверить отсутствие секретов и лишних файлов;
- отправить материалы до 10:00 МСК.

## Правило эскалации

Если зависимость не готова:
1. отметить BLOCKED;
2. указать конкретный недостающий вход;
3. сообщить руководителю;
4. перейти к независимой задаче, не создавая фиктивный контракт;
5. вернуться после снятия блокировки.

## Ежечасный статус

Каждый ответственный сообщает:
- что завершено;
- что проверено фактически;
- какие тесты прошли;
- что блокирует;
- что будет следующим;
- есть ли конфликт файлов или интеграций.

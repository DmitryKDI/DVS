# Архитектура — «Цифровой механик»

Состояние: целевая архитектура для согласования. Не является описанием уже реализованной системы.

## 1. Архитектурный подход

Модульный монолит с единым Backend API и явными границами модулей. Не создавать отдельные микросервисы или независимых LLM-агентов без доказанной необходимости.

## 2. Логические компоненты

| Компонент | Ответственность |
|---|---|
| Frontend | Автопарк, карточка автомобиля, диагностика, доказательства, проект заявки, подтверждение |
| Backend API | Валидация запросов, маршрутизация сценариев, авторизация при наличии требований |
| Vehicle Registry | Загрузка и выдача данных автомобилей |
| Diagnostic Adapter | Вызовы ML-заглушки по OpenAPI |
| Diagnostic Normalizer | Проверка и нормализация ответа без потери исходных данных |
| Document Ingestion | Извлечение текста и структуры PDF |
| Document Retrieval | Поиск с фильтрацией по семейству двигателя и метаданным |
| Evidence Validator | Проверка источника, страницы и применимости |
| AI Orchestrator | Управление последовательностью и подготовка объяснения |
| Maintenance Adapter | Вызов заглушки ТОиР по фактическому контракту |
| Audit Layer | История диагностик, подтверждений, отправок и ошибок |

## 3. Поток данных

Frontend → Backend API → Vehicle Registry → Diagnostic Adapter → внешний ML API → Diagnostic Normalizer → AI Orchestrator.

AI Orchestrator получает:
- нормализованный результат диагностики;
- сведения о выбранном автомобиле и двигателе;
- результаты Document Retrieval;
- проверенные Evidence от Evidence Validator.

Далее формируется объяснение и проект заявки. Отправка выполняется только после отдельного действия пользователя и проверки неизменности подтверждённой версии заявки.

## 4. Основные архитектурные правила

- Внешние интеграции изолированы адаптерами.
- Внутренние модели не должны копировать внешний API без необходимости.
- Исходные ответы внешних сервисов сохраняются для аудита в допустимом объёме.
- Ошибки транспорта, валидации и бизнес-логики различаются.
- LLM не является источником технических фактов.
- Результат поиска не считается доказательством до проверки применимости.
- Любое утверждение о процедуре должно ссылаться на проверенный фрагмент.
- Изменение заявки после подтверждения аннулирует прежнее подтверждение.
- Повторная отправка должна контролироваться механизмом идемпотентности, если это поддерживается контрактом ТОиР; иначе поведение явно ограничивается и тестируется.

## 5. Доказательство из PDF

Минимальные атрибуты Evidence:
- идентификатор документа;
- исходное имя файла;
- семейство двигателя / область применимости;
- индекс страницы PDF (с нуля или с единицы — единообразно зафиксировать);
- напечатанный номер страницы, если присутствует;
- исходный фрагмент;
- контекст;
- метод извлечения;
- статус проверки применимости.

Индекс страницы PDF и печатный номер страницы — разные атрибуты. Не подменять один другим.

## 6. Состояния сценария

Диагностика и заявка — разные жизненные циклы. Не смешивать статус HTTP-запроса с результатом диагностики.

Для заявки предусмотреть как минимум логические состояния:
- DRAFT;
- AWAITING_CONFIRMATION;
- CONFIRMED;
- SUBMISSION_PENDING;
- SUBMITTED;
- SUBMISSION_FAILED;
- CANCELLED.

Это внутренние проектные обозначения, не внешний контракт. Перед реализацией сопоставить их с фактическим API ТОиР.

## 7. Предлагаемый стек

Требует подтверждения по фактическому окружению:
- Frontend: React + TypeScript;
- Backend: Python + FastAPI;
- схемы и валидация: Pydantic;
- PDF: PyMuPDF или эквивалент после проверки документов;
- тесты: pytest, интеграционные и E2E;
- хранение: минимально достаточная БД, выбор после анализа сценариев.

Не устанавливать стек как неизменное требование, если предоставленная среда или стартовый проект диктуют совместимый вариант.

## 8. Неопределённости

До изучения полного OpenAPI и образцов запросов/ответов нельзя утверждать:
- точные URL и методы;
- обязательные поля;
- названия статусов;
- смысл confidence/anomaly_score;
- пороги принятия решений;
- механизм авторизации;
- гарантии идемпотентности ТОиР.

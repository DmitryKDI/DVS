# Командный регламент

## 1. Роли

### Дмитрий — руководитель проекта и системный интегратор
- архитектура и приоритеты;
- контроль backlog;
- постановка задач Codex;
- контроль Git и интеграции;
- приёмка модулей;
- разрешение блокировок;
- финальная демонстрация и сдача.

### Участник №1 — Backend / ML Integration / RAG
- фактические API-контракты;
- ML Adapter и нормализация;
- реестр автомобилей;
- PDF ingestion;
- поиск и проверка доказательств;
- Maintenance Adapter;
- интеграционные тесты Backend.

### Участник №2 — Frontend / QA
- пользовательские потоки и интерфейс;
- состояния загрузки и ошибок;
- отображение доказательств;
- проект заявки и подтверждение;
- тестовые сценарии;
- ручная проверка и регрессия;
- подготовка демонстрации.

Уровень опыта участников влияет на распределение поддержки и сложности поручений, но не снижает критерии качества.

## 2. Единый источник истины

- Репозиторий — источник актуальных документов и кода.
- Архитектурные решения фиксируются в docs/DECISIONS.md.
- Блокировки фиксируются в docs/KNOWN_LIMITATIONS.md.
- Изменения требований отражаются в backlog и матрице требований.
- Личные переписки не заменяют фиксацию решений.

## 3. Работа с одним общим Codex

- Codex получает одну активную задачу за раз.
- Перед новой задачей проверяются ветка, рабочее дерево и последние изменения.
- Не запускать конкурирующие задания на одни и те же файлы.
- Не просить Codex менять архитектуру без согласования.
- После выполнения обязательны diff, тесты и отчёт.
- Следующая задача начинается после проверки результата предыдущей.

## 4. Git

Рекомендуемые ветки после старта:
- main — стабильная интегрированная версия;
- feature/backend-ml;
- feature/rag-documents;
- feature/frontend;
- feature/maintenance-integration.

В main попадают только проверенные изменения. Перед слиянием проверяются тесты и отсутствие случайных файлов, секретов и незавершённых изменений.

## 5. Формат отчёта исполнителя

**Задача:** ID и название.  
**Статус:** PASS / FAIL / BLOCKED / NOT RUN.  
**Результат:** что фактически сделано.  
**Изменённые файлы:** полный перечень.  
**Коммиты:** ссылки или SHA.  
**Проверки:** команды и фактический вывод.  
**Дефекты:** обнаруженные проблемы.  
**Ограничения:** что не реализовано.  
**Блокировки:** что требуется.  
**Следующий шаг:** конкретное действие.

## 6. Качество постановок

Каждая задача содержит цель, контекст, входные данные, требования, ограничения, граничные случаи, безопасность, критерии приёмки, тесты, артефакты и условия блокировки.

Запрещены расплывчатые поручения вроде «подключи ИИ», «сделай RAG» или «почини интерфейс» без измеримого результата.

## 7. Статусы

- PASS — критерий проверен фактическим запуском.
- FAIL — проверка проведена, найдено несоответствие.
- BLOCKED — отсутствует необходимая информация или зависимость.
- NOT RUN — проверка не выполнялась.

Просмотр кода сам по себе не является доказательством прохождения runtime-критерия.

# Инженерные постановки задач

Документ задаёт содержание задач для реализации после официального старта. Это спецификации работ, а не конкурсный исполняемый код, конфигурации или готовые рабочие промпты.

## Общий стандарт для всех задач

Каждая задача должна иметь:
- ID и приоритет;
- ответственного и ревьюера;
- цель и измеримый результат;
- входные материалы и их версии;
- точные контракты;
- границы изменения;
- функциональные и нефункциональные требования;
- негативные и граничные случаи;
- критерии приёмки;
- тесты и фактические команды;
- список изменённых файлов;
- известные ограничения;
- условия BLOCKED.

Запрещено:
- угадывать неизвестные API;
- подменять отсутствующие данные синтетическими;
- молча менять единицы, коды или типы;
- маскировать ошибки fallback-ответами;
- заявлять PASS без запуска теста;
- смешивать семейства двигателей;
- отправлять заявку без подтверждения.

## BE-001 — ML Adapter

**Приоритет:** P0  
**Ответственный:** Backend / ML Integration  
**Ревьюер:** Дмитрий  
**Зависимости:** проверенный OpenAPI ML, примеры запросов/ответов, тестовая среда.

### Цель
Обеспечить типобезопасный и проверяемый вызов внешнего ML-сервиса.

### Объём
- изолировать сетевое взаимодействие в отдельном адаптере;
- реализовать запрос строго по OpenAPI;
- валидировать входные данные;
- обрабатывать успешный ответ и документированные ошибки;
- задавать таймауты в соответствии с требованиями среды и контракта;
- не выводить секреты в логи;
- сохранять correlation ID, если он предусмотрен контрактом или введён внутренне.

### Требования
- транспортные ошибки отделены от ошибок валидации и бизнес-отказов;
- неизвестный статус не трактуется как нормальный или аномальный;
- raw response сохраняется в допустимом объёме;
- повтор запроса не выполняется автоматически, если операция может быть неидемпотентной или контракт этого не допускает;
- внешняя схема не заменяется самодельной.

### Критерии приёмки
1. Сформированный запрос соответствует OpenAPI.
2. Успешный ответ валидируется.
3. Неизвестное поле/статус обрабатывается безопасно.
4. Timeout и недоступность сервиса дают отдельный контролируемый результат.
5. Секреты не попадают в логи и Git.
6. Есть unit и integration тесты.

### Обязательные тесты
- валидный ответ;
- HTTP ошибка;
- timeout;
- недоступный хост;
- невалидный JSON;
- неполный ответ;
- неизвестное enum значение;
- повторный вызов в условиях неопределённого результата.

### BLOCKED
Нет OpenAPI, нет примера обязательных полей, нет доступа к заглушке или неясна семантика критических статусов.

### Артефакты
Код адаптера, тесты, описание контракта, примеры безопасных логов, отчёт.

## BE-002 — Нормализация диагностического результата

**Приоритет:** P0  
**Ответственный:** Backend  
**Ревьюер:** Дмитрий  
**Зависимости:** BE-001, подтверждённая семантика ответа ML.

### Цель
Преобразовать внешний ответ в внутреннюю модель без потери значимых данных и без изменения смысла.

### Требования
- mapping каждого поля документирован;
- неизвестные поля не отбрасываются бесследно, если нужны для аудита;
- единицы измерения сохраняются;
- null, отсутствие поля и пустое значение различаются, если это значимо;
- confidence/anomaly_score интерпретируются только по документации;
- статус сбоя и плохого качества обрабатывается по фактическим кодам;
- нормальный результат не порождает ремонтную заявку.

### Критерии приёмки
- есть таблица mapping external → internal;
- для каждого преобразования указан источник;
- тесты покрывают граничные значения и неизвестные значения;
- нормализация воспроизводима.

### BLOCKED
Нет определения полей, статусов, шкал или единиц измерения.

## BE-003 — Реестр автомобилей

**Приоритет:** P0  
**Ответственный:** Backend  
**Ревьюер:** QA  
**Зависимости:** vehicles.json.

### Цель
Загружать и предоставлять корректные сведения об автомобилях.

### Требования
- читать исходный JSON без ручного переписывания данных;
- проверять схему и уникальность идентификаторов;
- сохранять исходное обозначение двигателя;
- определять семейство двигателя только по явным данным/подтверждённому mapping;
- неизвестная модификация не должна автоматически приравниваться к похожей;
- ошибки импорта должны быть диагностируемыми.

### Критерии приёмки
- загружено ожидаемое число записей (контрольное ожидание — 50; фактическое сверяется с файлом);
- нет дублирующихся ID;
- все записи имеют проверенное или явно неизвестное семейство;
- тесты на повреждённый JSON и неизвестный двигатель проходят.

### BLOCKED
Отсутствует vehicles.json или в нём нет достаточных данных для идентификации двигателя.

## RAG-001 — Извлечение PDF с provenance

**Приоритет:** P0  
**Ответственный:** Backend / RAG  
**Ревьюер:** Дмитрий + QA  
**Зависимости:** исходные шесть PDF.

### Цель
Получить поисковые фрагменты, которые можно однозначно сверить с исходным PDF.

### Требования
- исходные PDF не модифицируются;
- для каждого файла фиксируется SHA-256;
- сохраняется имя, версия/редакция, число страниц;
- каждый chunk связан с конкретным PDF и физической страницей;
- индекс страницы PDF хранится отдельно от напечатанного номера;
- таблицы и схемы не превращаются в якобы достоверный текст без проверки;
- страницы с плохим извлечением помечаются;
- извлечённый фрагмент можно открыть и сверить с оригиналом.

### Критерии приёмки
- все доступные PDF учтены;
- тестовые фрагменты возвращают правильную страницу;
- повторная обработка того же файла даёт согласованный результат;
- контрольные суммы совпадают с исходниками.

### BLOCKED
Нет исходных PDF, не удаётся определить страницу или извлечение критически искажает содержание.

## RAG-002 — Фильтрация по семейству двигателя

**Приоритет:** P0  
**Ответственный:** Backend / RAG  
**Ревьюер:** Дмитрий  
**Зависимости:** BE-003, RAG-001, подтверждённая матрица применимости.

### Цель
Не допускать выдачи процедур из неприменимого руководства.

### Требования
- фильтрация применяется до ранжирования или как обязательное ограничение retrieval;
- общая инструкция доступна только при документированной применимости;
- неизвестное семейство не даёт права искать по всем документам;
- фильтр виден в диагностическом trace;
- найденный документ содержит метаданные применимости.

### Критерии приёмки
- запрос для каждого семейства не возвращает документы, явно исключённые матрицей;
- неизвестный двигатель вызывает безопасный отказ;
- тесты покрывают ЗМЗ-40904.10 и ЗМЗ-40905.10 отдельно, даже если для них есть общее руководство.

### BLOCKED
Не подтверждена применимость руководств или отсутствуют точные данные двигателя.

## RAG-003 — Retrieval и верификация Evidence

**Приоритет:** P0  
**Ответственный:** Backend / RAG  
**Ревьюер:** Дмитрий + QA  
**Зависимости:** RAG-001, RAG-002.

### Цель
Возвращать доказательства, которые поддерживают конкретное техническое утверждение.

### Требования
- retrieval возвращает источник и страницу;
- evidence проверяется на соответствие вопросу и двигателю;
- совпадение терминов само по себе не считается доказательством;
- исходный текст не переписывается в цитате;
- контекст до/после учитывается для сохранения смысла;
- при конфликте источников конфликт показывается, а не скрывается;
- при отсутствии достаточного evidence возвращается состояние «не найдено подтверждение».

### Критерии приёмки
- каждый выданный evidence открывается на исходной странице;
- ручная выборочная проверка подтверждает точность цитаты;
- неподходящий двигатель исключается;
- отсутствие источника не приводит к генерации процедуры.

### BLOCKED
Нельзя подтвердить исходную страницу, применимость или смысл извлечённого фрагмента.

## AI-001 — Объяснение результата

**Приоритет:** P0  
**Ответственный:** Дмитрий + Backend  
**Ревьюер:** QA  
**Зависимости:** BE-002, RAG-003.

### Цель
Подготовить понятное объяснение, не превращая вероятностный результат в подтверждённый диагноз.

### Структура ответа
- что показала диагностика (только фактические поля);
- что это может означать (гипотеза, с указанием неопределённости);
- чем потенциально опасно продолжение эксплуатации (только при наличии основания);
- что предписывает руководство (только VERIFIED evidence);
- чего система не смогла подтвердить;
- рекомендуемый следующий шаг — проверка специалистом.

### Требования
- LLM не создаёт технические факты;
- каждое утверждение о процедуре привязано к evidence;
- выводы отделены от цитат руководства;
- при отсутствии evidence нет конкретной ремонтной инструкции;
- запрещены категоричные диагнозы при низком качестве или неизвестной семантике результата;
- сохраняется связь с входной диагностикой и версиями источников.

### Критерии приёмки
- проверка на наборе примеров показывает, что unsupported claims не выдаются за факты;
- ссылки ведут к правильным документам и страницам;
- негативные сценарии дают безопасный отказ.

### BLOCKED
Не подтверждены семантика ML-результата или доказательства процедуры.

## WO-001 — Формирование проекта заявки

**Приоритет:** P0  
**Ответственный:** Backend  
**Ревьюер:** Дмитрий + QA  
**Зависимости:** AI-001, контракт ТОиР.

### Цель
Создать редактируемый проект заявки из подтверждённых входных сведений.

### Требования
- проект заявки связан с автомобилем и диагностическим событием;
- причина/основание не усиливается сверх подтверждённых данных;
- работы не назначаются моделью самостоятельно;
- поля и обязательность определяются только контрактом ТОиР;
- неподтверждённые поля помечаются или исключаются;
- отсутствие процедуры не маскируется общими ремонтными рекомендациями.

### Критерии приёмки
- сформированный проект проходит валидацию;
- все поля имеют источник или обозначены как вводимые специалистом;
- можно просмотреть проект до отправки;
- проект не отправляется автоматически.

### BLOCKED
Нет схемы ТОиР или не определено, какие поля обязательны.

## WO-002 — Подтверждение и отправка

**Приоритет:** P0  
**Ответственный:** Backend + Дмитрий  
**Ревьюер:** QA  
**Зависимости:** WO-001, фактический контракт ТОиР.

### Цель
Обеспечить отправку только после явного подтверждения неизменённой версии проекта.

### Требования
- пользователь видит все отправляемые поля;
- подтверждение связано с конкретной версией/хешем содержимого;
- любое изменение после подтверждения сбрасывает подтверждение;
- повторное нажатие не приводит к неконтролируемому дублю;
- обработка неопределённого результата отправки учитывает фактическую поддержку идемпотентности;
- успех показывается только при подтверждённом успешном ответе ТОиР.

### Критерии приёмки
- без подтверждения отправка невозможна;
- изменение проекта требует повторного подтверждения;
- timeout не отображается как гарантированный отказ или успех;
- повторная отправка безопасно обрабатывается по контракту.

### BLOCKED
Нет документированного поведения ТОиР для повторов/таймаутов или нет возможности связать подтверждение с отправляемым содержимым.

## DEMO-001 — Финальная демонстрация

**Приоритет:** P0  
**Ответственный:** Дмитрий + Frontend/QA.

### Требования
- непрерывное видео до 3 минут в соответствии с правилами организатора;
- показывается реальный запуск;
- демонстрируется только фактически работающий функционал;
- в кадре видны документ и страница, подтверждение заявки и ответ ТОиР;
- нет монтажа, скрывающего ошибки, если это запрещено условиями;
- подготовлен запасной сценарий на случай недоступности внешней заглушки, при этом он не выдаётся за реальный live-вызов.

### Критерии приёмки
Видео воспроизводится, укладывается в лимит и соответствует фактическому состоянию репозитория.

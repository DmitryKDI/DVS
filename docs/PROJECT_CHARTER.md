# Устав проекта — «Цифровой механик»

Версия: 1.0  
Состояние: подготовительный документ

## 1. Цель

Создать адаптивное веб-приложение для поддержки механика автопарка: получить диагностический результат из внешнего ML-сервиса, объяснить его в контексте конкретного двигателя, найти применимую процедуру в технической документации и подготовить заявку на ТОиР с обязательным подтверждением специалиста.

## 2. Целевой сквозной сценарий

1. Выбор автомобиля из автопарка.
2. Получение диагностических данных и вызов внешнего ML API.
3. Проверка технического статуса и полноты ответа.
4. Определение семейства двигателя по исходным данным автомобиля.
5. Поиск процедуры только в применимой документации.
6. Формирование объяснения с разделением фактов, гипотез и документально подтверждённых сведений.
7. Подготовка проекта заявки.
8. Просмотр заявки специалистом.
9. Явное подтверждение конкретной версии заявки.
10. Отправка через предоставленную заглушку ТОиР и отображение фактического результата.

## 3. Исходный масштаб

Автопарк — 50 машин:
- ЯМЗ-236М2 — 13;
- ЯМЗ-536 — 12;
- ЗМЗ-5234.10 — 13;
- ЗМЗ-40905.10 — 8;
- ЗМЗ-40904.10 — 4.

Предусмотрены 14 типов неисправностей F01–F14, ориентировочно 3–5 проверок на автомобиль и шесть PDF-документов. Состав и применимость документов должны быть подтверждены по исходным материалам организатора.

## 4. Входит в объём

- интеграция с предоставленной ML-заглушкой;
- обработка диагностических состояний и ошибок;
- реестр автомобилей;
- обработка PDF и поиск процедур;
- проверка применимости документа;
- объяснение результата с доказательствами;
- подготовка заявки на ТОиР;
- подтверждение и отправка заявки;
- журналирование ключевых действий;
- веб-интерфейс;
- автоматизированные и ручные испытания.

## 5. Не входит в объём

- разработка собственной ML-модели;
- обработка исходных аудиозаписей собственной моделью;
- голосовой интерфейс;
- автоматическое назначение ремонта;
- отправка заявки без подтверждения;
- неподтверждённые интеграции;
- заявления о промышленной готовности, точности, экономии или внедрениях без измерений.

## 6. Непереговорные ограничения

1. Внешние API реализуются только по фактической OpenAPI-спецификации.
2. Неизвестные поля и статусы не выдумываются.
3. Нельзя смешивать документы разных семейств двигателей.
4. У каждого доказательства должны быть документ и точная страница PDF.
5. Неподтверждённая гипотеза не превращается в установленный диагноз.
6. Отсутствие процедуры нельзя компенсировать генерацией инструкции.
7. Низкое качество данных и сбой диагностики не должны приводить к диагнозу.
8. Отправка заявки возможна только после явного подтверждения пользователя.
9. Изменение заявки после подтверждения требует нового подтверждения.
10. Ошибка внешней системы не отображается как успешная операция.

## 7. Приоритеты

- P0 — сквозной сценарий и безопасность.
- P1 — надёжность, полнота обработки и удобство.
- P2 — дополнительные функции, не влияющие на приёмку основного сценария.

## 9. Критерий успеха

Работающий, воспроизводимо запускаемый сквозной сценарий от выбора автомобиля и получения диагностического результата до обоснованного проекта заявки и её отправки после подтверждения пользователя. Все критические ограничения должны быть проверены тестами.
